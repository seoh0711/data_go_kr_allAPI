# Outcome 중심 서비스 제작 기준

2026-10-30 사용자 지시를 다음 제작부터 적용한다. 이 문서는 기존 작업·환경·아틀라스 하위 배포·기존 API 연결·GitHub 반영·보안 제약을 대체하지 않는다. 새 프로젝트/환경·키/권한·유료 서비스·추적/분석 도구·예약을 만들지 않는다.

## 1. 먼저 읽고 기준선을 정한다

현재 진행·서비스 목록·remote·브랜치·diff를 확인한다. 진행 중 제작은 먼저 끝내며 중복 실행/주제를 피한다. 직전 서비스와 가장 관련된 기존 서비스의 실제 소스·화면·자료/연결 상태를 점검한다. 문서에서 읽은 과거 검증과 이번에 직접 관측한 결과를 구분한다. 비교 대상이 같으면 그 이유를 쓰고, 다르면 두 대상을 모두 기록한다.

[회차 템플릿](improvements/TEMPLATE.md)을 복사해 `docs/improvements/<회차>-<서비스>.md`에 작성하고 [이력](improvements/README.md)에 연결한다. 대상 버전/URL·데이터 버전·점검일·범위를 남긴다. 기존 서비스는 측정을 위해 수정하거나 재배포하지 않는다.

## 2. 구현 전에 과업·목표를 고정한다

대상 사용자와 문제, 완료할 대표 과업, **핵심 outcome 하나**를 정한다. 예를 들어 ‘정보를 본다’보다 ‘공식 근거가 있는 후보를 선택하고 문의할 정보를 빠짐없이 준비한다’처럼 종료 상태와 산출물이 관찰 가능해야 한다. 실제 전화·신청·예약이 승인되지 않았다면 준비 완료를 과업의 끝으로 정한다. 준비 완료를 실제 이용/수혜로 확대하지 않는다.

검색→이해→비교→선택→다음 행동의 각 단계에서 기존 지원 여부와 이번에 완성할 구간을 적는다. 모든 단계를 무조건 늘리지 않고 사용자가 막히는 연결을 해결한다. 범위 밖 단계와 연결되지 않은 정보는 명시한다.

다음 세 축을 모두 작성한다. 각 축에 개선 목표·측정 지표/단위/산식·기준선·목표값·시나리오·완료 기준을 둔다.

|축|유효한 발전의 예|발전으로 단정할 수 없는 것|
|---|---|---|
|기능|후보 비교 근거를 같은 기준으로 확인, 다음 행동에 필요한 정보 완결, 오류 후 과업 복귀|버튼/필터/API/화면 수만 증가|
|UI/UX|자료 범위·조건·미연결 상태를 구분할 수 있는 표시, 키보드 초점과 모바일 흐름, 불필요한 왕복 감소|색상/장식 변경만으로 이해도 향상 주장|
|사용자 과업 완료|정의된 과업 산출물의 정확성/누락/복귀를 검증, 핵심 outcome에 도달하는 대리 과업의 개선|테스트 통과율·배포 성공을 실제 사용자 성과로 치환|

도메인이 다르면 서로 다른 과업의 초/클릭/성공률을 직접 우열 비교하지 않는다. ‘공식 근거 확인→조건 이해→후보 선택→다음 행동 준비’ 등 공통 과업 구조와 동일 품질 기준을 정하고 각 도메인의 시나리오를 대응시킨다. 시간/단계를 비교하려면 시작·끝·입력·자료량·화면·캐시/네트워크·실패 조건·시도 수가 비교 가능함을 먼저 설명한다.

## 3. 미측정을 숫자로 채우지 않는다

미측정·미실행·측정 불가·목표 미달·통과는 서로 다른 상태다. 빈칸이나0을 미측정 대신 쓰지 않는다. 기준선이 미측정이면 먼저 관찰 가능한 대리 지표와 측정 시나리오를 정하고, 구현 전에 실제 측정해 목표값을 고정한다. 실제 outcome 자체는 계속 미측정일 수 있으며 대리 지표와 따로 적는다. 비교할 기준선을 얻지 못하면 그 항목의 개선은 미검증으로 남긴다.

지표에는 분자/분모·시도 수·단위·시작/종료·누락/오류 판정·측정 방식·반복/중단/재시도 규칙을 쓴다. 대상별 과업 성공 건수는 실제 수행한 시도만 기록한다. 작은 에이전트 시나리오의 결과를 사용자 전환율로 부르지 않는다. 과거의 카탈로그 로딩 시간, API 행 수, 테스트 수는 기술/자료 검증 증거이며 문의 준비 시간·이해도·만족도 기준선으로 재사용하지 않는다.

목표값은 기준선 관측 후 구현 전에 작성한다. 가설/잠정 목표는 그 상태를 표시한다. 관측 뒤 목표/분모/시나리오를 유리하게 바꾸지 않는다. 변경이 필요하면 원래 계획·이유·새 계획과 재측정 범위를 함께 남긴다.

## 4. 승인된 연결 안에서 구현한다

12,051 API 카탈로그와 실제 제공기관 문서를 근거로 조합을 고른다. 자료 출처·수집/기준일·범위·실시간/스냅샷/예시를 표시한다. 미연결 값·현재 이용 가능·자격·제휴 관계를 만들지 않는다. 기존 API와 서비스의 유용한 품질을 보존하고 모바일·키보드·빈 결과·오류·부분 실패·미연결 상태를 포함한다.

기존 API 연결만 사용한다. 새 인증 목적지/키/지속 접근·비용·공개범위·추적 권한을 지표 달성 수단으로 추가하지 않는다. 기존 보류 API를 무단 재호출/우회하지 않는다. 필요한 연결/설정 안내는 비밀값 없이 기록한다. 기존 환경이 연결되지 않으면 다른 환경으로 대체하지 않고 차단을 보고한다.

## 5. 증거의 종류와 한계를 분리한다

|종류|증명할 수 있는 범위|증명하지 못하는 것|
|---|---|---|
|자동화/계약/빌드|검사한 로직·조건·자료 형식·화면 동작|사람의 이해·만족·실제 이용|
|에이전트 대리 과업|고정 시나리오에서 확인한 정보·단계·누락·복귀|실사용자 성과/행동의 인과 효과|
|사람 사용성 검증|명시한 참여/과업/환경의 관찰 결과|전체 사용자 전환율·성과 일반화|
|실사용자 outcome|허용된 근거와 범위에서 실제 확인한 결과|측정하지 않은 시간 절감·만족도·지원 수혜|

사람 검증은 이미 허용된 참여/자료가 있을 때만 한다. 이 기준 자체가 초대·외부 연락·사용자 추적/개인정보 수집의 승인은 아니다. 실사용자 자료가 없으면 그 사실과 ‘대리 지표 검증’임을 명시한다. 증거에는 공개/가상 고정 입력만 사용하고 실제 개인 위치·건강·소득·연락처 등을 기록하지 않는다. 스크린샷/로그를 그대로 Git에 올리지 말고 검토한 비밀값 없는 문서·적절한 검사 코드만 포함한다.

## 6. 최종 과업 검증과 인계

최종 코드에서 모바일, 키보드, 빈 결과 후 복귀, 부분/전체 실패와 재시도, 미연결 상태를 대표 과업으로 검증한다. 동일 조건의 기준선→목표→관측→증거를 기록하고 유지할 기존 품질도 회귀 확인한다. 실패/미달은 승인 범위에서 개선·재검증하며 미실행/차단/정확히 모르는 원인은 숨기지 않는다. 테스트 중 소스 수정으로 개발 서버가 재로딩되지 않도록 입력을 고정한다.

기존 배포 절차와 운영 검증 후 관련 변경만 기존 `work`에 커밋·정상 push하고 원격 SHA를 직접 확인한다. 배포/GitHub 반영/기술 검증/대리 지표 달성/실사용자 outcome을 각각 판정한다. 기술적으로 게시됐어도 목표 미달이면 부분 완료/미검증 성과를 명시한다. 다음 회차가 재현할 기준선·보존할 품질·시나리오/지표 버전·남은 미달을 이력에 남긴다.
